# Code Engineering Pattern Analyzer v4.0

A local-first, heuristic analyzer that estimates **AI-like, automation-like, and generated-code characteristics** in Python and Java repositories. Operates entirely offline — no ML models, no external APIs, no source code leaves the machine.

> **Critical positioning:** This tool does **not** detect AI-generated code with certainty.
> It measures heuristic signals statistically correlated with generated, templated, or mechanically produced code.
> Results are **directional pattern indicators**, not forensic proof of AI origin.
> High scores may reflect senior clean code, strict formatters, framework conventions, DTOs, or generated clients.

## What this tool measures

The analyzer scans source code and produces per-file and per-repository estimates of:

- **AI-likeness**: How much code style resembles AI-assisted or mechanically generated code
- **Automation-likeness**: Structural regularity, repetition, scaffolding patterns
- **Engineering risk**: Which files most need manual review regardless of AI origin
- **Test quality**: Shallow assertions, mock abuse, generic fixtures in test files
- **Generated-code ratio**: How much of the repository is generated, vendored, or boilerplate

It is best understood as a **directional proxy for AI-assisted development adoption**, suitable for:
- Repository-level trend monitoring
- Team-level adoption signals
- Changed-code monitoring
- Generated-code governance
- Manual review prioritization

### What it does NOT measure

- It does **not** prove that any code was generated by an AI system
- It does **not** identify which developer wrote specific code
- It does **not** produce legally or contractually valid AI-origin certificates
- It does **not** distinguish Copilot suggestions from full AI generation
- It does **not** determine quality or correctness of code

## Quick start

```bash
# Default scan (heuristic analysis)
python -m ai_pattern_analyzer --dirs ./my-repo

# Full analysis with AST, entropy, git, and framework detection
python -m ai_pattern_analyzer --dirs ./repo --profile full

# CI pipeline scan (output JSON for dashboards)
python -m ai_pattern_analyzer --dirs ./repo --profile ci --format json > report.json

# Leadership summary in Markdown
python -m ai_pattern_analyzer --dirs ./repo --profile leadership --format markdown

# SARIF output for code scanning integration
python -m ai_pattern_analyzer --dirs ./repo --profile full --format sarif > findings.sarif

# Generate config file template
python -m ai_pattern_analyzer --generate-config > ai-analyzer.yaml

# Scan with config file
python -m ai_pattern_analyzer --dirs ./repo --config ./ai-analyzer.yaml
```

## Multi-score model

v4.0 introduces multiple score dimensions instead of a single AI score:

| Score | Range | Description |
|---|---|---|
| `ai_likelihood` | 0–1 | Raw heuristic aggregate, sigmoid-normalized |
| `adjusted_score` | 0–1 | ai_likelihood adjusted for file category, framework context |
| `risk_score` | 0–1 | Engineering review priority (≠ AI-likeness) |
| `confidence` | 0–1 | Signal agreement fraction — how consistent are the signals? |
| `kpi_score` | 0–1 | Repo-level AI-adoption proxy (production logic files only) |

### raw_score vs adjusted_score

**Raw score** reflects heuristic signals only — what patterns look like without context.

**Adjusted score** accounts for:
- **File category**: DTO classes, mappers, and generated code are expected to look regular — their adjusted score is reduced accordingly
- **Framework context**: Spring @RestController, JPA entities, MapStruct mappers, Pydantic models — these frameworks enforce patterns that look AI-like; the adjusted score accounts for this
- **Criticality**: Files in `critical_paths` get higher risk scores

**Example:** A MapStruct mapper might have raw_score=0.65 (AI-like patterns) but adjusted_score=0.22 (correctly interpreted as framework boilerplate, not AI generation).

### risk_score

Risk score reflects the priority for manual engineering review. It combines:
- Adjusted AI-like signal × confidence
- File category multiplier (production logic = 1.0, DTO = 0.4, test = 0.55)
- Critical path flag (increases risk by 35%)
- Framework boilerplate context (reduces risk if framework explains patterns)

A high risk_score means "this file warrants review" — not "this file was AI-generated."

### confidence and uncertainty_reasons

Low confidence means signals point in different directions. Uncertainty reasons explain why:
- "No Git history available"
- "DTO category — elevated signals may reflect structural regularity"
- "Framework detected (spring-boot) — some signals may be explained by conventions"
- "Only 3 active signals — limited coverage"

## File classification

Every file is classified into a semantic category before scoring. Category affects interpretation and adjusted score.

| Category | Adjustment Factor | Examples |
|---|---|---|
| `production_logic` | 1.00 (no adjustment) | Service classes, domain logic, controllers with business logic |
| `dto_mapper` | 0.60 | DTOs, request/response classes, MapStruct mappers, Pydantic schemas |
| `test` | 0.80 | Test classes, pytest files, JUnit tests |
| `generated` | 0.20 (excluded from KPI) | OpenAPI clients, Protobuf stubs, generated sources |
| `boilerplate_integ` | 0.55 | Spring Boot configuration, application startup |
| `config_infra` | 0.70 | application.yml, pom.xml, Dockerfile, CI config |
| `migration` | 0.65 | Flyway/Alembic migrations, schema changes |
| `example` | 0.60 (excluded from KPI) | Demo code, tutorials, playground |
| `vendor` | 0.10 (excluded from KPI) | Vendored libraries, third-party copies |
| `notebook` | 0.75 | Jupyter notebooks |
| `unknown` | 0.90 | Could not classify |

Generated, vendor, and example files are excluded from KPI calculation by default. The report shows how many files were excluded and why.

## Methodology

### Analysis layers

| Layer | Description | Flag/Always |
|---|---|---|
| Heuristic signals | 27 language-specific code-style signals | Always |
| Framework detection | Spring, JPA, Lombok, MapStruct, FastAPI, Pydantic, Django | Always |
| File classification | FileCategory for context-aware scoring | Always |
| Placeholder/LLM residue | Instructional comments, generic literals | Always |
| Test quality | Assertion quality, mock abuse, fixture realism | Always (test files) |
| Structural motifs | Method-level structural patterns, intra-file variance | Always |
| AST structural | Python AST: depth uniformity, function length, node diversity | `--ast` |
| Lexical entropy | Shannon entropy, type-token ratio, shingle repetition | `--entropy` |
| Cross-file similarity | TF-IDF cosine similarity across repository | `--similarity` |
| Git metadata | Commit bursts, author diversity, message entropy | `--include-git` |

### Stronger heuristic signals

High discriminating power between AI-like and human-like code based on calibration against real repositories (5,500+ files):

| Signal | What it detects | Delta (AI avg vs Human avg) |
|---|---|---|
| Type annotations (Python) | Full annotation coverage | +67% |
| Comment density | Over-commenting relative to code | +49% |
| Docstring quality | Structured Args:/Returns:/@param blocks | +38-54% |
| Stream API usage (Java) | Stream API over traditional loops | +45% |
| Function name length | Long, descriptive method names | +23% |
| Empty catch absence (Java) | No empty catch / printStackTrace | Discriminating |
| Exception style | Specific exceptions + reraise/from-chaining | Discriminating |

### Weaker or context-dependent signals

Lower weight; require corroboration:

| Signal | Confounders |
|---|---|
| Log quality | Team logging standards |
| Error message quality | User-facing services need rich messages |
| Lombok annotations | Project requires Lombok by standard |
| Optional usage | Modern Java style guide requirement |

### Token repetition / lexical entropy

Low entropy = few token types reused heavily. This appears naturally in:
- DTO classes with repeated field access
- Mappers with symmetric field assignments
- Generated API clients with repeated method patterns

High token repetition alone is **not** a reliable AI signal. It is a supporting signal only.

## Scoring interpretation

| Score Band | Range | Interpretation |
|---|---|---|
| **Low** | 0–25% | Patterns consistent with typical hand-written code for this language |
| **Moderate** | 26–50% | May reflect tooling, framework conventions, clean-code standards, or AI-assisted development |
| **Elevated** | 51–75% | Warrants contextual review: team conventions, tooling, code generation, development history |
| **High** | 76–100% | Strong AI-like or generated-like characteristics. Does not constitute proof of AI origin. |

The **adjusted score** (not raw likelihood) is the primary interpretation metric. Raw likelihood reflects signal aggregation without context; adjusted score accounts for file category and framework boilerplate.

**Confidence** < 0.40 means the classification should be treated as uncertain regardless of score.

## KPI usage

The `kpi_score` is the primary metric for AI-assisted development adoption tracking.

**Suitable use:**
- Repository-level trend monitoring over time (is adoption increasing or decreasing?)
- Team-level comparison across repositories controlling for language and code type
- Changed-code monitoring (what is the AI-like signal in new code vs. old code?)
- Supporting broader AI adoption programs alongside developer surveys and IDE telemetry

**How to interpret correctly:**
- **Directionally**: trend over time, not a point-in-time absolute
- **Comparatively**: how does one repo compare to another?
- **At aggregate level**: repository or team level, not individual file or developer
- **In combination**: alongside other signals, not as sole evidence

**KPI excludes**: generated, vendor, and example files. This is transparent in the report.

## Recommended usage

- Repository-level trend monitoring over sprints or quarters
- Team-level AI adoption proxy metric
- Identifying files that are candidates for manual review
- Generated-code governance (detecting growing proportion of generated code)
- AI-readiness analysis (identifying safe and risky areas for AI-assisted development)
- Engineering leadership dashboards as one of multiple indicators
- PR-level monitoring for high-risk production logic additions

## Non-recommended usage

- **Judging or evaluating individual developers** based on scores — the tool does not support this and results would be misleading
- **Contractual or compliance claims** about AI-generated code percentages
- **Exact measurement** of AI contribution in code reviews
- **Security or legal classification** of code origin
- **Replacing engineering code review** with automated verdicts
- **Disciplinary action** against developers based on scores
- **Ranking individual developers** by AI-like signal

## False positives and negatives

### False positives (high score, likely not AI-generated)

- **Senior developer code**: Clean, consistent, well-documented code from experienced engineers
- **Strict formatters**: Black, google-java-format, isort, Prettier produce uniform code
- **Generated boilerplate**: DTOs, OpenAPI clients, Protobuf stubs, JPA entities, schema mappers
- **Enterprise CRUD patterns**: Standard layered architectures with service/controller/repository
- **Heavy refactoring**: Large uniform cleanup or extraction refactors
- **Framework conventions**: Spring Boot, Quarkus, Django, FastAPI enforce regular patterns
- **Lombok-heavy Java**: Annotation-driven design that compresses boilerplate

**Mitigation**: Adjusted score and framework context reduce false positives for these cases. File category classification (DTO_MAPPER, GENERATED, BOILERPLATE_INTEG) explicitly accounts for them.

### False negatives (low score, may be AI-generated)

- **Human-edited AI output**: Developer significantly rewrote AI-generated code
- **Copilot incremental**: Small suggestions accepted across many commits, mixed with human edits
- **Intentionally irregular AI**: Prompted to match existing team style
- **Terse AI code**: Short utility functions, simple lambdas with few AI-like signals
- **Mixed-origin files**: The score reflects the aggregate; individual sections may differ
- **Junior developer code**: May look similar to AI code in irregularity

## Privacy and security

- **No source code leaves the machine**: All analysis runs locally. No API calls, no telemetry, no external services.
- **Air-gapped compatible**: No network dependencies. Works without internet access.
- **No code execution**: The analyzer reads source text only. It never imports or executes analyzed Python/Java code.
- **No secret extraction**: The analyzer does not extract or log secrets, credentials, or PII from source files.
- **Author data**: Git author information is used only for aggregate commit pattern analysis. Individual author scoring requires explicit opt-in (`enable_author_analysis = true`) and is disabled by default.
- **Privacy mode**: `privacy_mode: local` (default) — only local paths and statistics in reports. `safe` mode excludes snippets and paths. `hash` mode for anonymized output.

## Output formats

### Table (default)
Terminal output with per-repository summary, module heatmap, score distribution, top risk files, high-AI-like files, and git signal breakdown. Colored by score band.

### JSON (`--format json`)
Full structured report with schema version, all file results, findings with evidence and alternative explanations, module summaries, category summaries, exclusions, false-positive candidates, and high-confidence candidates.

```json
{
  "schema_version": "4.0",
  "scoring_model_version": "4.0",
  "disclaimer": "...",
  "repos": [{
    "repo": "my-repo",

      "ai_like_pct": 3.2
    },
    "files": [{
      "path": "src/Service.java",
      "category": "production_logic",
      "ai_likelihood": 0.547,
      "adjusted_score": 0.312,
      "risk_score": 0.218,
      "confidence": 0.61,
      "classification": "mixed",
      "review_recommendation": "review_as_boilerplate",
      "findings": [{
        "rule_id": "signal.docstring_quality",
        "description": "Structured docstrings with Args:/Returns: or @param/@return",
        "score_contribution": 0.082,
        "confidence": 0.72,

          {"explanation": "Team enforces Javadoc documentation standards", "likelihood": "high"}

      }]

```

### Markdown (`--format markdown`)
Human-readable report with executive summary, per-repository detail, module heatmap, high-risk candidates, review checklist, and methodology notes. Suitable for GitHub/GitLab PRs and documentation wikis.

### CSV (`--format csv`)
One row per file with: repo, file, language, category, kind, lines, ai_likelihood, adjusted_score, risk_score, confidence, classification, recommendation.

### SARIF (`--format sarif`)
SARIF 2.1.0 output for integration with code scanning systems (GitHub Advanced Security, VS Code SARIF Viewer). Findings with rule definitions and alternative explanations. Rules are informational — no security vulnerabilities are claimed.

## Architecture

```
scan repository
→ classify files (FileCategory)
→ detect framework context
→ parse source (AST for Python; regex for Java)
→ extract signals (heuristic, lexical, structural, placeholder, test quality)
→ apply rules → raw score
→ apply context adjustments (category factor, framework factor)
→ calculate adjusted score, confidence, uncertainty reasons
→ calculate risk score
→ aggregate by file / module / category / repo
→ produce reports (table / JSON / Markdown / CSV / SARIF)
```

### Extension points

Clear extension points exist for future integration:
- **JavaParser/Spoon**: Replace regex structural analysis with full Java AST
- **LibCST/tree-sitter**: Add CST-level formatting and style fingerprints
- **Semgrep/CodeQL**: Add security context signals
- **Git blame + file history**: Add churn weighting and new-code separation
- **CODEOWNERS**: Team-level report routing (never individual scoring)
- **PR metadata**: GitHub/GitLab API for review depth signals
- **Test coverage XML**: Coverage-aware risk scoring
- **OpenRewrite detection**: Mechanical modernization classifier

Each extension point has a documented interface and graceful fallback behavior. The analyzer continues with lower confidence when external data is unavailable.

## Limitations

1. **Heuristic-only**: Scores reflect pattern matching, not semantic understanding
2. **False positives**: Senior clean code, strict formatters, DTOs, framework boilerplate, generated clients all score higher than expected
3. **False negatives**: AI code manually edited, Copilot incremental suggestions, terse code, intentionally messy AI code all score lower than expected
4. **No ground truth**: Without labeled data from the same repository, calibration is approximate
5. **Language limitations**: Python and Java have full signal support. Other languages have reduced coverage.
6. **No intent**: The tool cannot determine whether elevated patterns were produced by AI, refactored by a human, or enforced by team standards
7. **Single-file granularity**: Mixed-origin files (partly AI, partly human) score as aggregates
8. **Version sensitivity**: Scoring model version 4.0 results are not directly comparable to v3.0 results

## Disclaimer

This tool detects **code-generation patterns** using statistical heuristics. It does not identify authorship, prove AI usage, or constitute evidence for any contractual, compliance, legal, or personnel claim. Results are probabilistic pattern signals and should be interpreted as directional trend indicators only.

High AI-likeness scores reflect stylistic and structural code characteristics — they are **not** a reliable measure of whether any specific code was generated by an AI system. Results must not be used to evaluate, discipline, or rank individual developers.
